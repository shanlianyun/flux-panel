## 特性

- 支持按 **隧道账号级别** 管理流量转发数量，可用于用户/隧道配额控制
- 支持 **TCP** 和 **UDP** 协议的转发
- 支持两种转发模式：**端口转发** 与 **隧道转发**
- 可针对 **指定用户的指定隧道进行限速** 设置
- 支持配置 **单向或双向流量计费方式**，灵活适配不同计费模型
- 提供灵活的转发策略配置，适用于多种网络代理场景

# 流量统计算法

## 流量流向定义

```
用户端 ←→ 转发服务器 ←→ 目标服务器/出口节点
```

### 数据流向说明

| 流向 | 描述 | 计费类型 |
|-----|-----|----------|
| 用户 → 转发服务器 | 用户发送到服务器的数据包 | 入站流量 |
| 转发服务器 → 目标服务器 | 服务器转发到目标的数据包 | 出站流量 |
| 目标服务器 → 转发服务器 | 目标服务器返回的数据包 | 入站流量 |
| 转发服务器 → 用户 | 服务器返回给用户的数据包 | 出站流量 |

## 计费模式

### 🔄 双向计费
统计所有方向的流量，包括：
- ✅ 用户 → 转发服务器
- ✅ 转发服务器 → 目标服务器  
- ✅ 目标服务器 → 转发服务器
- ✅ 转发服务器 → 用户

**计费公式**：`总流量 = 入站流量 + 出站流量`

### ➡️ 单向计费
仅统计有效的转发流量，包括：
- ❌ 用户 → 转发服务器 （不计费）
- ✅ 转发服务器 → 目标服务器 （计费）
- ❌ 目标服务器 → 转发服务器 （不计费）
- ✅ 转发服务器 → 用户 （计费）

**计费公式**：`总流量 = 转发出站流量`

## 使用场景

- **双向计费**：适用于需要精确计量所有网络资源消耗的场景
- **单向计费**：适用于用户友好的计费模式，只对实际的数据转发服务收费

> 💡 **提示**：可以在创建隧道时选择不同的流量计算方式，灵活适配不同的业务需求

### 一行命令打开面板管理菜单

在服务器执行（需要 Bash、curl、Python 3.8+ 和支持 JSON 配置的 Docker Compose v2）：

```bash
curl --fail --location --retry 3 https://raw.githubusercontent.com/shanlianyun/flux-panel/main/panel_install.sh -o panel_install.sh && bash panel_install.sh
```

- **已有原作者系统：选 `7`「旧版迁移到本 fork」**，确认脚本建议的原部署目录，再按提示输入 `yes`。
- **已迁移到本 fork：选 `2` 更新**；普通更新不会隐式迁移旧系统。
- **全新安装：选 `1`**，使用专用空目录；发现旧容器、数据卷或同名 Compose 项目就停止。
- `4` 导出数据库/配置备份；`8` 恢复中断的迁移/更新。脚本不会再自动删除自己，之后可直接运行 `bash panel_install.sh`。

管理脚本默认使用数字菜单，直接运行即可：

```bash
bash panel_install.sh
```

菜单中选择：`1` 全新安装、`2` 更新、`4` 备份、`7` 旧版迁移、`8` 恢复中断操作。命令行子命令仅供自动化维护。

脚本检查数据库结构和剩余空间，先备份、拉取完整 `sha-提交号` 镜像，再只替换前后端；保留旧端口、网络、数据卷及其他服务，不重启 Docker、MySQL 或节点，不自动执行改表 SQL。目标镜像尚未发布、备份失败或部署不兼容时会停止。**这不是任意旧版本的通用升级器**；建议先在备份副本验证，正式切换需要短暂维护窗口。

失败时会尝试回退原容器和配置，**绝不自动回灌数据库**。基础健康检查不代替登录、WebSocket、隧道和流量验证。完整支持范围、备份说明及高级手动方式见[迁移指南](docs/migrate-from-original.md)。

默认跟随 `main` 对应的完整 SHA 镜像；请先确认该提交的前后端镜像发布成功。如需指定已验证版本，可运行：

```bash
PANEL_IMAGE_TAG=sha-替换为40位完整提交号 bash panel_install.sh
```

原有 `docker-compose-v4.yml` / `docker-compose-v6.yml` 仍保留原作者镜像，供检查和兼容旧部署；新的安装菜单使用 `docker-compose-fork-v4.yml`。已有 IPv6 网络在迁移时原样保留，不自动修改 Docker daemon 配置。

节点端：
```bash
./install.sh

```

**原作者旧节点也需要单独升级，面板更新不会替换节点程序。** 必须使用本 fork 的新版脚本；原作者旧脚本的 `2. 更新` 仍会下载原作者程序。先确认目标节点 Release 已发布，再灰度一台节点。旧节点兼容边界与升级步骤见[旧节点升级说明](docs/legacy-node-upgrade.md)。

全新节点在面板“节点管理”页面复制一条安装命令即可；短命令通过 `node.sh` 引导脚本处理私有临时目录、安装脚本下载检查和清理，不覆盖当前目录文件。安装命令包含节点密钥，请勿公开分享或复用其他节点身份。已有节点运行脚本后在菜单中选择 `2. 更新`，不建议选择 `1. 安装`覆盖配置。脚本会校验 GOST 二进制、保留节点配置，并在更新失败时恢复旧版本；脚本本身不会自动删除。

节点上报和控制通道默认保留 HTTP/WS 兼容旧部署；公网部署必须先配置面板 TLS 反向代理，再使用 `GOST_PANEL_SCHEME=https ./install.sh` 安装或更新节点，使节点使用 HTTPS/WSS。该变量会写入生成的 systemd 服务环境中。

管理面板维护期间（不重启节点服务、不改动规则），节点上的 GOST 转发服务不会因为 WebSocket/HTTP 控制通道暂时断开而停止；节点会在面板恢复后自动重连并重新同步规则。维护窗口内不能通过面板执行新增、编辑、暂停或删除操作，节点本地已运行的规则仍继续提供服务。

默认情况下安装脚本直接从 GitHub 下载，不会通过第三方代理，也不会向 IP 定位服务查询所在地。若你的网络必须经由可信镜像，可在运行前显式设置 `GITHUB_MIRROR_PREFIX`；请自行确认镜像服务的可信度。
